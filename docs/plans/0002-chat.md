# 0002 — Chat: site and team groups

Status: draft
Brief: none

## Intent

WhatsApp groups are created and maintained by hand, so their membership drifts from reality - they might keep members which are not a real employees long ago or have no new incoming members at all for a long time. Here every site has a group and every team at a site has a group, and membership follows the member record: a new hire is in the right groups on day one, someone moved to another site is moved with no one doing it (by the system not a manager), and a leaver is gone the moment they are deactivated.

Nobody manages group membership.

## Acceptance criteria

1. A member sees exactly two groups: their site's group and their site-and-team group. They see no other groups.
2. A member added to a site and team sees those groups and the newest 200
   messages in each, without any further action.
3. A member whose site or team changes stops seeing the old groups and sees the new ones, without any further action.
4. A message posted to a group appears for every other member viewing that group, without reloading.
5. A member cannot read or post to a group they do not belong to.
6. A message is text, 1 to 2000 characters. An empty or longer message is rejected with a visible and human-readable validation error.
7. Each group shows an unread count for the member; opening the group clears it.

## Out of scope

- Direct messages, ad-hoc groups, group admin.
- Media, files, reactions, replies, editing, deleting.
- Push notifications. The next thing to build.
- Search, typing indicators, presence.

## Implementation plan

### Rulings on the criteria

Answered before planning went further; each is recorded here rather than left
to a session's judgement.

1. **Team, not role.** Invariant 7's "site and **role** groups" is the wrong
   word; criteria 1–3 govern. Step 12 amends invariant 7 and supersedes
   DECISIONS 0004.
2. **Criterion 3 gets a context function, no UI.** `Members.update_assignment/3`
   — actor first, manager only, same tenant, liveness re-read. No member-edit
   screen in 0002.
3. **A new hire's unread count is zero.** First sight of a group with no read row
   seeds `last_read_seq` to that group's current maximum, so the history of
   criterion 2 arrives already read.
4. **Body is trimmed, then measured in graphemes.** Leading and trailing
   whitespace is stripped before the 1–2000 check, so a whitespace-only body is
   empty and rejected. `char_length` in the database check constraint counts the
   same units.
5. **Own messages never count as unread, and an open group stays at zero.** Each
   message arriving in a mounted `GroupLive` marks the group read.
6. **A moved member's open session is not ejected.** Next mount is enough;
   posting from the stale view fails because `post_message/3` re-reads the
   member. No assignment-change broadcast.
7. **A zero unread count renders nothing** — the badge element is absent.
8. **History is capped at the newest 200 messages**, with no load-older control.
   Criterion 2 was amended to say so, on your instruction, so the plan and the
   criterion now agree. Messages older than that are retained (invariant 8) and
   simply unreachable in 0002.

### Groups are rows; membership is a predicate

Group membership is never stored. A member's two groups are:

    site group   groups where site_id == member.site_id and team is null
    team group   groups where site_id == member.site_id and team == member.team

`members.site_id` and `members.team` are NOT NULL and teams are a closed list
of three (`Members.Member.teams/0`), so every site has exactly four groups: one
site group and three team groups. Membership is derived at query time from the
member record, which is re-read where it is acted on (DECISIONS 0008).

Rejected: no `groups` table at all, with each message carrying `site_id` and a
nullable `team` and group identity being that tuple. It removes a table, but
every route, PubSub topic, stream dom id and unread row then needs a composite
key or a synthetic encoding of one, and `/chat/:id` loses a real id to
authorize.

Rejected: creating group rows lazily, on first open, with an upsert. It drops
the backfill migration and the cross-context call from `Members.create_site/2`,
at the cost of a write on every read path. Revisit only if step 1's backfill
proves awkward.

### Tenant comes from the acting member, not from an argument

Every `Chat` function takes the acting member first (invariant 5) and derives
the tenant from `member.tenant_id`, through one private helper that also
re-reads the member's `active` flag — the `still_active/1` shape
`Members.deactivate_member/2` already uses. Deriving the tenant from a member
record resolved from the authenticated session is not deriving it from a param,
so invariant 2 holds; the prefix still reaches Ecto only through
`Tenancy.prefix/1`.

Rejected: `(tenant, member, ...)` signatures. The tenant would be redundant with
`member.tenant_id`, every function would have to assert the two agree, and a
caller could pass a mismatched pair.

Cost: one extra query per `Chat` call. It buys fail-closed behaviour on
deactivation for every chat function without each one remembering to ask.

### Unread is an integer cursor, not a timestamp

`messages` carries a `seq` bigserial. Unread count is
`count(messages where group_id = ? and seq > last_read_seq and member_id != ?)`
— the member's own messages are never unread — and opening a group writes
`last_read_seq = max(seq)`.

A member's first sight of a group seeds that cursor to the group's current
maximum instead of 0, so the history they inherit counts as read (ruling 3).
Seeding happens lazily, in `list_groups/1` and `get_group/2`, rather than at
member creation: the same path then covers a member moved to a new site
(criterion 3), and `Members` does not have to call into `Chat`. Cost: a read
path that writes one row per group, once per member. `timestamps` are `:utc_datetime`
(second granularity) throughout 0001, so a timestamp cursor would drop or
double-count messages posted in the same second. The sequence lives in the
tenant schema, so it cannot leak a global message volume across tenants.

### Data changes

Tenant only (`priv/repo/tenant_migrations/`, one new migration). No public
migration: nothing about chat belongs to `public` (invariant 1).

- `groups` — `site_id` references `sites` (same schema, a real FK), `team`
  string nullable, timestamps. Two unique indexes, because Postgres treats NULL
  as distinct: `unique_index(:groups, [:site_id], where: "team IS NULL")` and
  `unique_index(:groups, [:site_id, :team])`. A check constraint restricts
  `team` to the three known values. No `name` column — the display name is
  derived from the site name and the team.
- `messages` — `group_id` references `groups`, `member_id` references
  `public.members` (`prefix: "public"`, `on_delete: :restrict`), `body` text NOT
  NULL with `check char_length(body) between 1 and 2000`, `seq` bigserial with a
  unique index, timestamps. Index `(group_id, seq)`. No delete path anywhere
  (invariant 8).
- `group_reads` — `group_id`, `member_id` (`prefix: "public"`), `last_read_seq`
  bigint NOT NULL, timestamps, primary key `(group_id, member_id)`. No default:
  the row is always written with a seeded value, and a default of 0 would make a
  missing seed look like "everything unread".
- Backfill, in the same migration: for each row of `sites` in that schema,
  insert the site group and the three team groups. The migration runs per
  tenant, and `sites` is in the same schema, so this is a local INSERT…SELECT.

### Web contract

Fixed here so that spec-tester has route names and selectors before
implementation, as step 7 of 0001 had to improvise.

- `/chat` — `ChatLive`, `:index`. Container `data-test-id="chat-groups"`; per
  group a link `data-test-id="group-<group_id>"` whose text is the display
  name, and `data-test-id="group-unread-<group_id>"` carrying the count — absent
  entirely when the count is zero (ruling 7).
- `/chat/:id` — `GroupLive`, `:show`. `data-test-id="group-title"`; one
  `data-test-id="message-<message_id>"` per message inside a stream, oldest
  first, at most the newest 200 (ruling 8);
  `data-test-id="message-form"` with field `message[body]`;
  `data-test-id="message-error"` for the criterion 6 message.
- A group id that is not one of the member's two — another site, another team,
  another tenant, or nonexistent — redirects to `/chat` with a flash. Same
  response for all four, so nothing reveals whether the id exists.
- Both routes go in the existing `:require_active_member` live_session, so
  invariants 3 and 4 are already enforced for them.

### Risks

- The backfill assumes no tenant schema has `groups` yet and that every member's
  `site_id` still names a live site. DECISIONS 0007 records that nothing
  enforces the latter; a member pointing at a deleted site would see one group,
  not two. No site deletion path exists, so this cannot happen yet.
- `member_id` foreign keys point at `public.members`, which the FK cannot
  restrict to the right tenant. `Chat` must check `member.tenant_id` against the
  group's tenant — structurally guaranteed here, since the group is read under
  that member's prefix, but a future writer bypassing the helper loses it.
- The 200-message cap is a product limit, not a storage one: older messages stay
  in the table with no way to read them. A later plan adding load-older must not
  assume any of them were trimmed.
- Lazy read-cursor seeding writes on a read path. Two concurrent mounts can race;
  the insert uses `on_conflict: :nothing` against the composite primary key, so
  the loser keeps the winner's cursor. Both compute the same value.
- Moving a member (step 6) leaves their `group_reads` rows for the old groups.
  Harmless — those groups become unreadable — but the rows stay.
- All chat tests touch a tenant schema, so all are `async: false`
  (`.claude/rules/testing.md`). The suite grows; the 30s note there may come due.

## Notes / deviations

- The backfill inserts nothing for a tenant created *after* this migration:
  `Tenants.create_tenant/1` provisions the schema through `Triplex.create/1`,
  which runs every tenant migration before any site exists. So `groups` is empty
  immediately after `mix ecto.reset`, and step 1's planned check — group count ==
  sites × 4 on a fresh database — could never have passed. Step 5's
  `Members.create_site/2` hook is what gives a new site its groups; the backfill
  exists only for a tenant whose schema predates the migration. It was verified
  by rolling the migration down and back up on the two seeded dev tenants, which
  do have committed sites: 8 groups and 2 site groups each, from 2 sites.
- `seq` is a `bigserial`, so its sequence lives in the tenant schema and no
  tenant can infer another's message volume from it.
